# 2026-11-12 夹爪驱动修正与保持/往返实测

最终结果：修正使能后的目标刷新并启用 Linux FTDI 低延迟后，RH-P12-RN 在 Mode 5 下通过三次当前位置保持、八次小行程往返，其中包含正式 `arm → command → wait → disarm` 接口的一次往返。当前使能已关闭，速度和电流为 0。旧故障锁已根据实测更新，`allow_motion`、步幅/会话范围、健康/电流检查及异常关闭仍生效。

## 修正与最终验证

1. 连接时调用 pyserial 的 `set_low_latency_mode(True)`。本机 FTDI 延迟由 16 ms 变为 1 ms，单寄存器往返约 1 ms。无需 sudo，也不写夹爪 EEPROM。若平台提供此接口但设置失败，保留只读能力，并在运动写入前报错；未提供此接口的平台不在本次实测范围内。
2. 保留使能前的位置/速度/电流上限预置，在使能成功后立即重发实测当前位置，之后才查询反馈。正式适配器与诊断程序均使用这个顺序，Mode 0 的目标电流初始化不变。
3. 保持阶段单独检查 ±3 个计数的目标偏差，不再沿用后续运动的宽范围。
4. 电流上限继续采用设备原有 820 raw，约 3.2964 A；PID D=200、I=0、P=30、模式 5、EEPROM 电流/位置限制和固件均未修改。

官方 [RN 示例](https://github.com/ROBOTIS-GIT/RH-P12-RN_Example/blob/33cd12b2486f1aeefdf5567aab9ca9bec59ec333/rh-p12-rn.cpp#L631-L639) 中，位置动作先使能再发送 Goal Position。本次据此设计对照测试。USB 延迟与目标刷新同时改变，未做单变量实验，因此不能断言其中任何一项是全部历史异常的唯一根因；下述实测支持这套组合修正在本机的有界使用。

| 验证 | 行程/次数 | 结果 |
|---|---|---|
| 独立对照：使能后发送附近新目标 | 222→230→222，1 次往返 | 到位并稳定，误差不超过 2 raw |
| 独立对照：使能后重发同一当前位置 | 3 次，每次保持 0.6 秒 | 各次相对起点波动不超过 2 raw |
| 更新后的诊断程序 | 223↔235，速度设置 4/8 raw 各 3 次往返，共 6 次 | 12 段运动全部到位并稳定，误差不超过 2 raw |
| 正式驱动 `arm/command/wait/disarm` | 224→236→224，1 次往返 | 到位读数 235、225，误差各 1 raw；退出后使能关闭 |

重复诊断中，速度设置 4 raw（0.456 rpm）时，命令发出至首次进入目标 ±2 raw 约 405–443 ms；设置 8 raw（0.912 rpm）时约 317–385 ms。命令 ACK 约 1 ms，反馈采样间隔中位数约 4 ms。到位时间是主机观察值，不是电机固有延迟或固定控制频率保证。速度反馈离散峰值有高于轮廓参数的样本，不将配置值等同于已经认证的实际速度上界。

六次往返的运动段采样电流峰值约 0.27738 A；使能保持阶段还记录到最高约 1.12158 A 的瞬态，均低于本次沿用的 3.2964 A 上限。未测量实际指尖力，不从这些电流值推算夹持力。最终正式接口读回：位置 225、目标 224、速度 0、电流 0、使能 0、硬件错误 0、供电约 22.9 V、温度 42℃。

没有进行完整 0..1150 行程、带负载接触、Mode 0 运动或严格实时验证。本次通过范围是空载小行程位置控制。

最小独立诊断入口（无需模型/PyTorch，输出目录需为新目录）：

```bash
PYTHONPATH=src .venv/bin/python -m neurofusion.gripper_benchmark \
  --stage small --operator-ready --output outputs/gripper-small-next
```

`--operator-ready` 表示现场确已固定、空载、清场并可随时断电。默认 SDK/串口依赖已安装在本机 `.venv`；完整模型依赖尚未安装。

## 首次保持失败（上述修正前）

首次诊断的 U2D2 通信和寄存器读写可用，但在当时初始化及设备最大电流上限下，夹爪未能保持当前位置。该次已中止且没有执行后续往返。以下保留原始失败证据，以便与修正后结果对照。

用户已确认夹爪固定、空载、活动区清空且可随时断电后，执行本次受控诊断。没有发送网络动作、切换模式、修改 EEPROM 电流限制、修改 PID 或升级固件。

## 实机与预置

- U2D2：`/dev/ttyUSB0`，稳定标识 `usb-FTDI_USB__-__Serial_Converter_FTBIHTGU-if00-port0`。
- 夹爪：RH-P12-RN，型号 35073，固件 25，ID 1，2 Mbps，Mode 5。
- 使能前：位置和目标均为 352；电流 0；电压约 23.4 V；温度 41℃；硬件错误 0；使能关闭。
- EEPROM Current Limit 保持原值 820 raw，按 RN 单位约 3.2964 A；本次 Goal Current 使用相同上限。
- 关闭使能时写入位置 352、速度 4 raw（约 0.456 rpm）、加速度 1 raw，逐项读回一致；再连续读取 596..625，确认目标及参数未变。

Mode 5 中 Goal Current 是位置控制的电流上限，Mode 0 中才是目标电流。速度参数 0 会关闭速度轮廓，不能作为停机指令。依据：[ROBOTIS RN 控制表](https://emanual.robotis.com/docs/en/platform/rh_p12_rn/)。

## 异常经过

原程序计划保持 0.6 秒，通过后才允许后续运动；本次实际提前触发保护。

| 阶段 | 目标 raw | 实测位置 raw | 实测速度 raw | 实测电流 raw | 电压 V |
|---|---:|---:|---:|---:|---:|
| 使能前块读取 | 352 | 352 | 0 | 0 | 23.4 |
| 使能后首次块读取 | 352 | 348 | -16 | -64 | 23.4 |
| 使能后第二次块读取 | 352 | 315 | -84 | -18 | 23.4 |

第二次反馈位置 315 越过原诊断范围 `[348,377]`，自动关闭使能并读回确认。两次反馈中速度配置始终为 4 raw、电流上限始终为 820 raw、位置目标始终为 352。首次采样电流约 -0.25728 A；这是有限采样中的读数，不是对启动瞬态电流的上界保证。

记录到的速度反馈幅值达到 84 raw，按官方单位约 9.576 rpm，超过预置的轮廓速度 0.456 rpm。不能把配置值视为本次异常期间实际运动速度的可靠上限；仍需独立核对反馈与物理运动。

从主机发出使能请求到关闭使能得到 ACK 约 96.46 ms，其中首次块反馈在约 32.07 ms 返回、第二次在约 80.32 ms 返回。这些时间来自主机单调时钟，不是机械启动/制动延迟或硬实时停止保证。

程序确认使能关闭后恢复原 RAM 电流/速度/加速度参数。关闭后仍读到位置继续变化，清理结束时位置 234、速度 -40 raw；此时目标 261 是清理中在关闭使能后预置的瞬时位置，不能误读为主动开合目标或已经到位。

随后独立只读复核：位置稳定在 222，速度 0，电流 0，使能 0，硬件错误 0，供电约 23.3 V、温度 41℃。之后用户明确确认没有断电、刚才确实观察到明显物理运动，并授权继续测试。后续对照与成功结果见前文。

本次直接证据表明：最大电流上限下仍然存在保持异常，不能宣布“增大电流后已修复”；使能期间目标寄存器没有归零，也不能以“目标被自动清零”解释。本次只证明寄存器读回与实际反馈不符合预期，不能据此断定编码器、机械、电机控制器或固件中的任何一个已经损坏。供电/温度和硬件错误位正常，也不等于机械控制正常。

后续用官方 SDK 独立读取已核对模式、位置/目标、PID、速度/电流及供电，操作员目视确认了首次异常中的真实运动；没有执行 Wizard 或固件升级。官方手册中使能切换影响坐标的说明不构成本次实际复位的证据。历史异常全部机理仍未完全分离，后续使用应保持本轮验证过的初始化和监测方式。

## 诊断停止保护修正

复查发现 `Bench.monitor()` 的保持阶段曾沿用后续运动的范围 `[origin-4,origin+25]`，会接受偏离原位 4 个计数的首次样本。现为使能保持阶段单独增加 ±3 计数约束，首个越界样本即抛出异常并进入原有关闭使能/恢复清理；后续运动范围维持原设置。

新增离线回归用例，模拟使能后在原通用范围内漂移 4 个计数，验证首个样本即中止、使能关闭、参数恢复且不发送后续运动目标。另覆盖使能后必须刷新目标的行为、刷新失败后的关闭/恢复、低延迟设置顺序与失败后只读/拒绝运动。该保护本身不替代前述启动顺序修正和实机验证。

最终 36 项驱动、位置诊断及电流入口测试通过；另有 2 项依赖 PyTorch 的模型/反馈集成测试因当前环境未安装 PyTorch 而排除。没有运行完整训练或模型测试。实机验证后另补充了连接状态重置与诊断低延迟失败拒绝路径，这些只读/失败路径由离线回归覆盖，没有为此再次使能实机。软硬件验证报告均在 JSON 归档中保留。
